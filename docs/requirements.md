# 《芝麻开门》需求文档

## 1. 项目背景

《芝麻开门》是基于课程样例 `world-of-zuul` 思想扩展的 Web 图形化文字冒险游戏。

原始样例是命令行文字冒险游戏，主要包含房间、出口、命令解析和游戏循环等基础结构。本项目将在此基础上进行主题重构和功能扩展，形成具备完整交互界面、游戏规则、状态管理和协作开发过程的课程实践项目。

本项目同时用于体现软件工程实践中的需求分析、面向对象建模、Git 分支协作、Issue 管理、Pull Request 合并、自动化测试和文档交付。

## 2. 项目目标

本项目最终实现一个前后端分离的 Web 图形化文字冒险游戏。

主要目标如下：

- 完成一个可运行的游戏项目。
- 实现金额、体力、负重、物品、暗语、救援和通关机制。
- 使用 Spring Boot 提供后端 REST API。
- 使用 Vue 3 实现图形化游戏界面。
- 使用 GitHub Issues、Milestones、Pull Requests 管理协作过程。
- 使用 Maven、JUnit 5 和 GitHub Actions 支持测试与自动化构建。
- 形成 README、REPORT、API 文档、测试文档和 AI 使用说明等交付材料。

## 4. 游戏背景设定

玩家扮演一名寻宝者，进入一座需要暗语开启的神秘秘窟。玩家每次进入秘窟需要支付入场费，进入后需要在不同房间之间移动、寻找线索、拾取物品、使用补给并找到最终出口。

秘窟中包含普通房间、补给房间、陷阱房间、线索房间、宝物房间和出口房间。玩家需要在有限的金额、体力和背包负重限制下规划行动路线。

正确暗语为“芝麻开门”。玩家在合适场景输入正确暗语后，可以开启关键区域或最终出口。

## 5. 核心规则

### 5.1 金额系统

- 玩家初始金额为 100。
- 玩家进入秘窟时需要支付入场费。
- 触发救援时需要支付救援费。
- 金额不足以支付必要费用时，游戏失败。

### 5.2 入场费规则

- 入场费为 10。
- 开始游戏或进入秘窟时扣除。
- 如果玩家金额不足以支付入场费，则不能开始探索。

### 5.3 体力系统

- 玩家初始体力为 30。
- 玩家最大体力初始为 30。
- 每次合法移动消耗 5 点体力。
- 补给物品可以恢复体力，但不能超过最大体力。

### 5.4 负重系统

- 玩家初始最大负重为 20。
- 玩家拾取物品后会增加当前负重。
- 当前负重加上目标物品重量超过最大负重时，不能拾取该物品。
- 装备类物品可以提高最大负重。

### 5.5 物品系统

物品分为以下类型：

| 类型 | 示例 | 作用 |
|---|---|---|
| TREASURE | 金币、宝石、金杯 | 用于最终结算，占用负重 |
| SUPPLY | 水袋、干粮、药剂 | 恢复体力 |
| EQUIPMENT | 背包、护符 | 提升最大负重或增强能力 |
| KEY | 古卷、钥匙 | 提供线索或解锁区域 |
| TRAP | 诅咒物品 | 产生负面效果，可选扩展 |

### 5.6 暗语机制

- 正确暗语为“芝麻开门”。
- 玩家在关键房间输入正确暗语后，可以开启宝库或最终出口。
- 输入错误暗语时，系统应返回提示信息。

### 5.7 救援机制

- 当玩家体力不足以继续移动时，触发救援机制。
- 救援会将玩家送回入口或安全房间。
- 救援费用为 25。
- 如果玩家金额不足以支付救援费用，则游戏失败。

### 5.8 通关机制

- 玩家到达最终出口并满足通关条件时，游戏胜利。
- 通关时可以展示玩家携带物品、剩余金额、剩余体力和结算信息。

## 6. 胜利条件

玩家满足以下条件时判定胜利：

- 到达最终出口。
- 已通过暗语或关键物品开启必要区域。
- 游戏状态未失败。

## 7. 失败条件

出现以下情况时判定失败：

- 金额不足以支付入场费。
- 金额不足以支付救援费。
- 玩家主动退出游戏。

## 8. 功能需求

### 8.1 后端功能需求

- 创建玩家、房间、物品和游戏会话模型。
- 初始化固定地图和初始游戏状态。
- 提供开始游戏、获取状态、移动、拾取、丢弃、使用物品、提交暗语和重新开始等接口。
- 实现金额、体力、负重、物品、暗语、救援、通关和失败规则。
- 返回统一 API 响应格式。
- 为核心业务逻辑编写 JUnit 5 单元测试。
- 后端类、构造器和公开方法应编写规范 Javadoc。

### 8.2 前端功能需求

- 展示玩家金额、体力、负重和当前位置。
- 展示当前房间名称、描述、出口方向和房间物品。
- 展示玩家背包物品。
- 提供开始游戏、移动、拾取、丢弃、使用物品和输入暗语等交互。
- 展示后端返回的提示消息和游戏日志。
- 展示救援、通关和失败提示。
- 前端构建应通过 `npm run build`。

### 8.3 文档与协作需求

- 使用 Issue 拆分任务并指定负责人。
- 使用 Milestone 管理阶段目标。
- 使用功能分支开发并通过 Pull Request 合并。
- 重要接口变化应同步更新 API 文档。
- 重要规则变化应同步更新需求文档。
- 报告中应说明 AI 使用情况。

## 9. 非功能需求

- 可维护性：后端采用分层结构，前端采用组件化结构。
- 可测试性：核心业务规则应有单元测试覆盖。
- 可扩展性：后续可扩展更多房间、物品和特殊规则。
- 可追踪性：功能开发过程应能通过 Issue、分支、提交和 PR 追踪。
- 可运行性：最终项目应提供明确的本地运行方式。
