# 《芝麻开门》需求文档

## 1. 项目背景

《芝麻开门》是基于课程样例 `world-of-zuul` 思想扩展的 Web 图形化文字冒险游戏。

原始样例是命令行文字冒险游戏，主要包含房间、出口、命令解析和游戏循环等基础结构。本项目在此基础上完成主题重构和功能扩展，形成具备三关探索、资源管理、物品、商店、暗语、存档、排行榜和图形化交互界面的课程实践项目。

本项目同时用于体现软件工程实践中的需求分析、面向对象建模、Git 分支协作、Issue 管理、Pull Request 合并、自动化测试和文档交付。

## 2. 项目目标

本项目实现一个前后端分离的 Web 图形化文字冒险游戏。

主要目标如下：

- 提供可连续完成的三关遗迹探索流程。
- 实现金币、体力、负重、物品、商店、暗语、当前关重开、失败和通关结算机制。
- 使用 Spring Boot 提供后端 REST API，并以后端 `GameState` 作为游戏状态权威来源。
- 使用 Vue 3 实现暗黑奇幻风格游戏 HUD、背包、商店、帮助、地图和结果弹窗。
- 支持注册、登录、SQLite 存档、读取存档、排行榜和历史最高分。
- 支持部署到云服务器，通过公网 IP 访问前端页面并调用后端接口。
- 使用 GitHub Issues、Milestones、Pull Requests 和 GitHub Actions 管理协作与质量检查。
- 形成 README、REPORT、API 文档、测试说明和 AI 使用说明等交付材料。

## 4. 游戏背景设定

玩家扮演一名寻宝者，支付入场费后进入神秘秘窟。秘窟由石门遗迹、月纹回廊和沉金王座三片区域组成，玩家需要在不同房间之间移动、寻找线索、拾取物品、管理资源，并通过营地商店补充物资或出售宝物。

玩家在有限的金币、体力和背包负重下规划路线。跨关进入只能通过营地的“继续探险”流程完成，不能通过普通移动返回上一关商店。

最终石门需要在机关长廊提交正确暗语后解锁。暗语答案为“芝麻开门”，但游戏通过日志、房间描述、物品描述、帮助说明和错误输入提示逐步提供线索，不在开局直接揭示完整答案。

## 5. 核心规则

### 5.1 金额系统

- 玩家初始金额为 100。
- 玩家开始新游戏时支付 10 金币入场费。
- 玩家可在营地商店购买补给和装备。
- 玩家可在营地商店出售 `TREASURE` 类型宝物。
- 通关时剩余宝物自动计入最终结算。
- 金额不足时不能完成对应购买或必要支付。

### 5.2 入场费规则

- 入场费为 10。
- 开始新游戏时由后端扣除。
- 如果玩家金额不足以支付入场费，则不能开始探索。

### 5.3 体力系统

- 玩家初始体力为 30。
- 玩家最大体力初始为 30。
- 每次合法移动消耗 5 点体力。
- 补给物品可以恢复体力，但不能超过最大体力。
- 体力不足或耗尽时，当前实现会按后端规则重新开始当前关，并通过消息和日志提示玩家。
- 前端不能自行扣除体力或模拟重开结果。

### 5.4 负重系统

- 玩家初始最大负重为 20。
- 玩家拾取物品后增加当前负重。
- 当前负重加上目标物品重量超过最大负重时，不能拾取该物品。
- 有实际负重效果的装备可提高最大负重。
- 丢弃或消耗物品后，当前负重由后端重新计算并返回。

### 5.5 物品系统

物品分为以下类型：

| 类型 | 当前示例 | 作用 |
|---|---|---|
| TREASURE | 铜月钥牌、银纹杯、星纹罗盘、王权短杖 | 用于商店出售或最终结算，部分宝物兼具路线条件 |
| SUPPLY | 清水、干粮、提神药剂 | 恢复体力，使用后消耗 |
| EQUIPMENT | 结实绳索、铁底靴 | 提升能力或作为后续特殊玩法扩展 |
| KEY | 残旧地图、开锁针、油灯 | 提供地图入口、线索或特殊机关条件，不一定能直接使用 |
| TRAP | 暂无正式物品 | 可选扩展类型，当前主流程未使用 |

物品规则：

- 物品包含 ID、名称、描述、类型、重量、体力效果、负重效果和价值。
- 玩家可拾取当前房间物品，也可将背包物品丢弃到当前房间。
- 补给可以恢复体力，有实际效果的装备可以提升能力。
- 前端按物品实际语义展示操作，普通关键物品和宝物不显示误导性的“使用”入口。
- 残旧地图作为关键物品；持有时可从主界面或背包查看地图，丢弃后不能继续查看。
- 铜月钥牌、星纹罗盘等物品兼具宝物价值和路线条件。
- 宝物可出售或用于通关结算。
- 油灯、开锁针、铁底靴等物品的更深入机关交互属于后续优化。

### 5.6 暗语机制

- 正确暗语为“芝麻开门”。
- 暗语只能在机关长廊提交。
- 后端通过 `canSubmitPassword` 告知前端当前是否允许打开暗语入口。
- 前端不得使用房间名称或其他猜测替代后端字段判断。
- 输入错误暗语时，系统根据输入内容和累计错误次数提供分层、递进提示。
- 暗语线索来自日志、房间描述、物品描述和帮助说明。
- 正确暗语解锁最终石门，正确与否以后端返回状态和消息为准。

### 5.7 当前关重开与提示机制

- 当玩家体力不足以继续移动或体力耗尽时，后端按规则重新开始当前关。
- 玩家可以主动使用“重开”操作重新开始当前关。
- 重开后的房间、玩家状态、日志和消息以完整 `GameState` 为准。
- 前端通过醒目提示展示体力不足、体力耗尽、重开和相关结果。
- 更复杂的救援费用或复活机制属于后续可选扩展，当前实现不依赖前端模拟。

### 5.8 通关机制

- 玩家完成三关探索、在机关长廊解锁暗语并进入最终石门后胜利。
- 通关时剩余宝物自动结算，并形成最终积分。
- 后端返回 `finalScore` 和 `highScore`。
- 前端显示明确的通关结果弹窗，并在通关后刷新排行榜。

## 6. 胜利条件

玩家满足以下条件时判定胜利：

- 通过两个营地商店流程进入第三关。
- 在机关长廊提交正确暗语并解锁最终石门。
- 到达最终出口。
- 游戏状态由后端返回为 `WON`。

胜利后：

- 剩余宝物参与最终结算。
- 后端返回最终得分和历史最高分。
- 前端展示通关结果，普通探索操作停止可用。

## 7. 失败条件

出现以下情况时可能判定失败或结束当前探险：

- 金额不足以支付开始游戏所需入场费。
- 后端规则判定游戏状态为 `FAILED`。
- 玩家主动放弃探险；放弃后清除当前会话并删除当前存档。

体力不足或耗尽当前按“重新开始当前关”处理，不直接由前端判定失败。失败状态和恢复结果均以后端返回为准。

## 8. 功能需求

### 8.1 后端功能需求

当前已实现：

- 创建玩家、房间、物品和游戏会话模型。
- 初始化固定三关房间图、玩家状态和物品来源。
- 提供注册、登录、开始游戏、获取状态、移动、返回、拾取、丢弃、使用物品、提交暗语、保存、读取、重开和放弃等接口。
- 提供商店商品目录、购买、出售和继续探险接口。
- 提供存档列表和排行榜接口。
- 实现金额、体力、负重、物品、商店、暗语、当前关重开、通关、失败和积分规则。
- 防止玩家通过普通移动或返回操作跨关回退；跨关只能通过商店继续探险。
- 使用 SQLite 保存用户、存档和历史最高分。
- 所有游戏状态变化由后端完成，并返回完整 `GameState`。
- 为核心业务逻辑编写 JUnit 5 测试，并使用 Checkstyle 检查代码风格。
- 支持在服务器环境以可执行 Jar 方式运行，并通过 Nginx 代理对外提供接口访问。

后续优化：

- 扩展油灯、开锁针、铁底靴等物品的真实机关交互。
- 完善异常恢复、旧存档兼容和更多端到端测试。

### 8.2 前端功能需求

当前已实现：

- 登录、注册、开始新游戏、继续最近存档和读取指定存档。
- 游戏主界面展示玩家金额、体力、负重、关卡、当前房间、房间描述、日志和操作入口。
- 行动面板展示可用方向，支持按钮、方向键和 R/H/Q/E/P 快捷操作。
- 支持拾取、丢弃、使用物品，并使用后端返回的完整 `GameState` 刷新页面。
- 背包弹窗展示分类、物品描述、效果、价值和当前可用操作。
- `SHOPPING` 状态自动显示商店面板，支持商品目录、购买、出售和继续探险。
- 帮助弹窗按操作、下一步、地图、背包和暗语分节提供引导。
- 持有残旧地图时可打开地图弹窗，并在地图图片上标记当前房间。
- 暗语入口和 P 快捷键由后端 `canSubmitPassword` 控制。
- 通关、失败和体力警告使用醒目弹窗展示。
- 排行榜使用真实后端数据，支持加载、空数据、失败和成功状态。
- 保存、重开、放弃、退出游戏和存档读取保持登录状态与会话状态一致。
- 前端通过 Vitest、ESLint 和 `npm run build` 进行检查。

后续优化：

- 为特殊路线宝物出售增加二次确认。
- 继续微调地图坐标、当前位置标记和 HUD 视觉细节。
- 将静态帮助说明扩展为动态下一步引导。
- 增加更多浏览器端到端流程测试。

### 8.4 部署与访问需求

当前部署方案：

- 使用阿里云轻量应用服务器作为发布环境。
- 服务器系统使用 Ubuntu 22.04。
- 后端 Spring Boot 项目打包为 Jar，并运行在服务器本机 `8080` 端口。
- 前端 Vue 项目通过 `npm run build` 构建为静态资源，并由 Nginx 对外提供访问。
- Nginx 监听 `80` 端口，负责展示前端页面，并将 `/api` 请求转发给后端服务。
- SQLite 数据库保存在服务器本地运行目录，用于保存用户、存档和排行榜数据。
- 服务器防火墙放行 `22`、`80`，后续需要 HTTPS 时放行 `443`。
- 部署文档记录服务器初始化、项目拉取、前后端构建、服务启动、日志查看和更新发布流程。

验收要求：

- 用户可以通过服务器公网 IP 打开游戏首页。
- 登录、注册、开始游戏、读取存档、保存游戏和排行榜接口在服务器环境可正常使用。
- 后端健康检查接口可在服务器本机返回 `{"status":"ok"}`。
- 关闭 SSH 连接后，后端服务仍可通过系统服务持续运行。
- 服务器运行时数据不提交到 GitHub。

## 9. 非功能需求

- 权威性：后端游戏状态是唯一权威来源，前端不得自行修改房间、体力、背包、日志或游戏结果。
- 接口兼容性：前端通过现有 `/api` 代理和 RequestParam 风格调用接口；HTTP 200 返回的 `GameState.message` 也可能表示业务未成功，前端仍需整体刷新并展示消息。
- 可维护性：后端采用分层结构，前端采用组件化结构，资源和布局配置集中管理。
- 可测试性：后端核心规则应有 JUnit 测试，前端关键 API 和组件状态应有 Vitest 测试。
- 可扩展性：后续可扩展更多房间、物品、机关交互、动态引导和地图表现。
- 可追踪性：功能开发过程应能通过 Issue、分支、提交和 PR 追踪。
- 可运行性：项目应提供明确的本地运行方式，前后端构建检查应可通过。
- 可部署性：项目应提供明确的云服务器部署方式，使前端页面和后端接口可以通过公网访问。
- 自动化：GitHub Actions 应执行后端测试/检查和前端 lint/test/build。
- 数据安全：不提交 `backend/data/`、`backend/target/`、`frontend/node_modules/`、`frontend/dist/`、`.npm-cache/` 等运行时数据或生成目录。
- Mock 约束：正式游戏交互以真实后端数据为准；已有 mock 仅可用于测试或必要兜底，不得冒充真实排行榜、商店商品或权威游戏状态。
